low_latency_grouped_gemm 当前实现导读

这个文件描述的是当前最快路径：low_latency_grouped_gemm/ 下的 packed-int4 weight / fp8 activation grouped GEMM。它不是 WGMMA/TMA persistent grouped GEMM；当前实现保留 packed int4 weight，在线解包并用 fp16 MMA 计算，重点优化小 token MoE decode 场景的 launch、schedule、cache 和寄存器流水。

  • active path: dsched_prebuilt
  • default scale group: 64
  • benchmark GPU: physical GPU 3
  • CTA tile: 8 tokens x 64 output rows

一眼看懂

生产路径把上游 routing/permute 的结果变成 compact token tile schedule，然后用 persistent CTA 固定步长消费。

原始 weight

uint8[G,N,K/2] packed int4，仍然按 int4 保存，不离线展开成 fp8 或 fp16。

scale 转置

输入 scale 先准备成 [G,N,K/group]，group 当前支持 64 和 128。

interleave kernel

launch_low_latency_grouped_gemm_interleave() 重排 int4 nibble，并把 scale padding 到每行 8 对齐。

常驻 buffer

得到 w_interleaved 与 scales_padded，decode 阶段重复使用。

token count

token_counts[g] 给出每个 expert 的实际 token 数，空 expert 不产生 token tile。

compact schedule

每个有效 8-token tile 生成一条 (tile_experts[t], tile_n[t])。

CTA-local 顺序

推荐上游按 cta_local 顺序写 schedule，改善 persistent CTA 的 weight 重用。

参数检查

模板分派

先按 kDeviceSchedule 和 kScaleGroupSize 分派，再按 K family 分派。

full-K path

K % 128 == 0；K >= 512 时启用 prefetch-A，优先走 K-const 实例。

tail64 path

K % 128 == 64；target192 FC2 的 K=192 走这个分支。

Kernel hot pathinclude/low_latency_grouped_gemm_kernel.cuh

persistent CTA

task = blockIdx.x; task += gridDim.x 固定步长遍历，不用 atomic 抢占任务。

task 解码

row_tile = task % row_tiles，token_task = task / row_tiles。

K-loop

LDG packed int4 weight + fp8 activation，转 half 后用 Mma<16,8,16> 累加 fp32。

bf16 store

每个 thread 写最多 2 token x 2 output row，最后乘 act_scale。

输入与 layout contract

名字上沿用了 GEMM A/B，但当前 kernel 内 A = weight，B = activation。

字段 layout / 含义 关键约束
acts fp8 e4m3 activation，[M_total,K]，token 已按 expert compact。 K 是 compute K，必须 64 对齐。
w_interleaved packed int4 weight，预处理后仍是 int4，按 [G,N_orig,K] 的 interleaved 访问模式保存。 字节数为 G * N_orig * K / 2。
scales_padded bf16 scale，[G,N_orig,padded(K/group,8)]。 group 只支持 64 或 128，且 K % group == 0。
token_counts / expert_offsets 每个 expert 的 token 数和在 compact activation/output 中的 row offset。 空 expert 不产生 tile；输出按 compact token 顺序写回。
tile_experts / tile_n compact schedule，每条任务表示一个 expert 的一个 8-token tile。 生产推荐 prebuilt + CTA-local 顺序；device build_each 是调试/便利路径。

当前 target shape：FC1 N=384,K=4096 走 full-K prefetch-A const path； FC2 N=4096,K=192 走 tail64 const path。使用 scale_group_size=64 时，FC2 刚好是 3 个完整 scale group，不需要 partial group 处理。

预处理：packed int4 interleave + scale padding

这一步通常按 layer/shape 初始化一次，不在每个 decode token 上重复做。

weight nibble 重排

low_latency_grouped_gemm_interleave_kernel<group> 对每个 (expert, output row, 64-K block) 处理一个 FragmentA。 原始 int4 nibble 在一个 32-bit word 里按 {0,1,2,3,4,5,6,7} 排列，预处理用 {0,4,1,5,2,6,3,7} 重排，匹配后续每个 thread 的 K-lane 和 MMA 输入拼装方式。

scale padding

scale 是 per-output-channel, per-K-group。预处理把每行 scale 数量 padding 到 8 的倍数：padded_sfs_per_row = ceil(K/group, 8)。 这样 kernel 内按 row 取 scale 时地址计算固定，不需要处理 scale row 的短尾。 

// 预处理入口
launch_low_latency_grouped_gemm_interleave(
    w_orig_padded, scales_n_major,
    w_interleaved, scales_padded,
    G, N_orig, K_compute, stream, scale_group_size);

// scale_group_size = 64 或 128，K_compute 必须整除 group。

Schedule 与 dispatch 逻辑

性能敏感路径是 device schedule + prebuilt compact schedule。

生产路径：dsched prebuilt
  • num_token_tiles_device != nullptr 选择 persistent device schedule。
  • build_device_schedule=false 时，GEMM 只消费上游已写好的 schedule。
  • launch grid 是 (persistent_ctas,1,1)，不按 expert 或 max_M_g 铺矩形网格。
device build_each
  • build_device_schedule=true 会先 launch schedule builder。
  • builder 对每个 expert 做 tiles=ceil(token_counts[g]/8)。
  • 用 atomicAdd(num_token_tiles, tiles) 写 compact schedule；这是便利路径，不是最佳生产路径。
host compact / rectangular
  • num_token_tiles > 0 是 host compact schedule。
  • 没有 schedule 时走 rectangular fallback，需要 max_M_g。
  • 这些路径用于对比和调试；生产目标是无 host sync 的 prebuilt dsched。
CTA-local schedule 顺序

上游先生成 expert-major 列表，再按 streams = ceil(persistent_ctas / row_tiles) 做转置：schedule[stream + k * streams] = next(expert_major)。 kernel 内每个 CTA 用 task += gridDim.x 固定步长消费，因此这个转置让同一个 CTA 的私有任务序列更常落在同一或相邻 expert，减少 weight cache 抖动。

row_tiles 与 task 展开

row_tiles = ceil((N_orig / 4) / blockDim.y) = ceil(N_orig / 64)。 每个 token tile 需要覆盖所有 output-row tiles，所以 persistent kernel 里的总任务数是 num_token_tiles * row_tiles。任务先映射到 row_tile，再映射到 schedule 里的 token_task。 

// persistent_device_schedule()
num_token_tiles = *params.num_token_tiles_device;
total_tasks = num_token_tiles * row_tiles;

for (task = blockIdx.x; task < total_tasks; task += gridDim.x) {
    row_tile = task % row_tiles;
    token_task = task / row_tiles;
    batch_idx = tile_experts[token_task];
    n_tile = tile_n[token_task];
    compute_tile(row_tile, batch_idx, n_tile, scheduled=true);
}

Launch family 分派表

这里的 const 指 K 是编译期模板常量，不是 runtime const int。

条件 kernel family 当前用途 优化点
scale_group_size == 64 kScaleGroupSize=64 当前生产默认。FC2 K=192 是 3 个完整 64-group。 每 64 K 独立 scale，scale load 和 scale multiply 更多，但满足新约束。
scale_group_size == 128 kScaleGroupSize=128 保留兼容路径。要求 K % 128 == 0。 两个 64 unroll 先累加，再乘一个 128-group scale。
K % 128 == 0 && K >= 512 w4a8_prefetch_a* FC1 K=4096、uniform128 FC2 K=512。 启用 A/weight register prefetch；优先 K-const 实例。
K % 128 == 0 && K < 512 w4a8_device_kernel 短 full-K fallback。 关闭 prefetch-A，避免短 K 下多一组 A fragment 的寄存器压力。
K % 128 == 64 w4a8_tail64* target192 FC2 K=192。 tail64 K-const 递归展开，最后一个 64 chunk 不需要第二 unroll。
full-K K-const + prefetch-A

launch_full_k_prefetch_const_if_supported() 支持 512/768/1024/2048/4096/8192。命中时会实例化 low_latency_grouped_gemm_w4a8_prefetch_a_const_*<group,K>， 让 row_stride_a、effective_K、scale row padding 等都进入编译期常量路径。 这就是当前代码里的 K-const prefetch-A 组合。

tail64 K-const

launch_tail64_const_if_supported() 支持 64/192/320/448/576/704/832/960。它用模板递归展开 128 + ... + 64，例如 target192 FC2 的 K=192 是一个 128 chunk 加一个 64 tail chunk。

CTA 内部计算模型

block=(8,16,1)，总 128 threads；一 CTA 处理一个 row_tile 和一个 8-token tile。

threadIdx.x
  • 范围 0..7。
  • 选择 K lane 和输出 token pair。
  • 每次 LDG 取 kElementsPerAccess=16 个元素。
threadIdx.y
  • 范围 0..15。
  • 选择 output row group。
  • idx_row_m = 4 * (row_tile * 16 + threadIdx.y)。
K unroll
  • kInterleaveBlockK=64。
  • kUnroll=2，一个 full iteration 覆盖 128 K。
  • tail64 path 最后一轮只跑一个 64 chunk。
MMA
  • int4 weight 和 fp8 activation 都转换成 half fragment。
  • 使用 CUTLASS Mma<16,8,16,F32F16F16>。
  • accumulator 是 fp32，最后写 bf16。

命名提醒：这里的 A-prefetch 指的是 weight 侧 packed int4 fragment。 当前 kernel 的 A 是 weight，B 是 activation；不要按常规 GEMM 习惯把 A 理解成 activation。

scale_group_size = 128

两个 64-K unroll 先累加到临时 frag_mma_accum，然后每个 output row 只加载一个 bf16 scale 并乘一次。这个路径 scale load 和 scale FMA 更少，但要求 K % 128 == 0。

scale_group_size = 64

每个 64-K unroll 独立乘自己的 scale。full 128 iteration 会尽量一次 global load 两个 scale；tail64 最后一段只用一个 scale。它让 K=192 这种 FC2 shape 成为无 partial group 的合法生产输入。

为什么这些优化能保留

当前实现只保留跨 shape 稳定收益的策略，避免单点 exact-shape hack。

prefetch-A 阈值
  • K=128 强制开启会明显变慢。
  • K=256 强制开启仍然变慢。
  • K=512 开始有稳定收益。
  • 因此 runtime 规则是 K % 128 == 0 && K >= 512。
K-const codegen
  • 减少动态 loop/tail 判断。
  • 让 effective_K、row_stride_a、scale padding 参与常量折叠。
  • 对 FC1 K=4096 和 FC2 K=192 都命中。
compact schedule
  • 只 launch 有 token 的 expert tile。
  • 避免 rectangular fallback 对空 expert / 空 tile 做无效工作。
  • CTA-local 顺序改善每个 persistent CTA 的 weight 访问连续性。

当前实现已经去掉旧的 M==4096 或 K==192 这类业务尺寸 exact 特判。 K=192 仍然很快，是因为它自然命中通用 tail64 K-const family，而不是因为 FC2 有单独 kernel。
